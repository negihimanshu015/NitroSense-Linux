🧠 The Rust Backend, Explained Simply

How the nitrosense-linux backend controls your Acer Nitro laptop's fans and RGB lights — without the jargon getting in the way.

🖥️ What is this app, and where does the backend fit?

nitrosense-linux is a desktop app for Acer Nitro laptops on Linux. It lets you control the fan speed, change the RGB keyboard lighting, and watch your CPU / GPU temperature.

The app is built with Tauri, which means it's really two parts:

  • The frontend — HTML, CSS and JavaScript (in the src/ folder). This is the pretty window you see and click around in.
  • The backend — Rust code (in the src-tauri/src/ folder). This is the engine that does the hard work: talking to the hardware.
Analogy: Think of the frontend as the driver's dashboard, and the Rust backend as the engine underneath the hood. You push a button on the dashboard, and the engine makes the wheels turn.

The backend is made of three files. Here they are:

FileJob
main.rsThe entry point. Sets everything up and exposes the "buttons" (commands) the frontend can press.
wmi.rsThe hardware talker. The only code that actually touches the fans, sensors and RGB lights.
config.rsThe "memory". Saves your settings to a file and loads them back later.

🔌 How the backend talks to the hardware

Acer laptops don't give you a friendly API to control the fans. Instead, they expose a hidden communication channel called WMI (Windows Management Instrumentation) — even on Linux.

On Linux, this channel can be reached through a special file called /proc/acpi/call. Yes, it's a file, but it's a virtual file — writing to it sends a command to the laptop's firmware, and reading from it gives you the reply. 

// A command to set the fans to "Auto mode"
\_SB.PC00.WMID.WMBH 0x0 0x0E b0900410000000000

Let's decode that command, because this is where it gets cool:

  • \_SB.PC00.WMID.WMBH — the address of the WMI device on the laptop's "motherboard bus".
  • 0x0E — the opcode (an operation code), telling the laptop "this is a fan-mode command".
  • b0900410000000000 — a buffer of data with the details: the fan sub-mode and some flags.
Why "0x0E"? 0x0E is just hexadecimal (base-16) for the number 14. It's an agreed-upon code: "0x0E means fan behavior", "0x10 means fan speed", "0x05 means read a sensor", "0x06 means set RGB color", "0x14 means set RGB mode". These codes come from reverse-engineering how Acer's own software talks to the hardware.

Different commands use different numbers, but the pattern is always the same: write a command, read back the answer.

📁 The three files, up close

1. wmi.rs — the hardware talker hardware

Everything that touches the actual laptop lives here. It's split into three groups of tasks:

Fans

The fans have three modes (auto, max, custom), and in custom mode you can set the speed for the CPU fan and the GPU fan separately, from 0% to 100%. The code clamps the number to 100 because the laptop's EC (embedded controller — a tiny computer inside the laptop that manages power) rejects anything above 100.

Sensors (temperature & fan speed)

Reading a temperature is also just a WMI command. The laptop answers with something that looks like {0x00, 0x37, 0x00, ...} — a list of hex numbers. The code parses that text and turns it into a normal number you can read, like "55°C".

One neat trick: if the GPU sensor returns 0 (because the GPU is fully asleep), the code falls back to reading temperature from Linux's hwmon system, or even from the nvidia-smi tool.

RGB lights

The keyboard has 4 zones (groups of keys), each with its own color. The backend can set each zone's color (red, green, blue), and the overall mode (static, breathing, neon, wave), speed and brightness.

2. main.rs — the "buttons" backend

This file defines the commands — the functions the frontend can call by name. Think of them as buttons on the dashboard. For example:

CommandWhat it does
set_fan_modeSwitch fans to auto / max / custom.
set_fan_speedSet CPU and GPU fan percentages.
get_telemetryGet CPU/GPU temperature and fan RPM.
get_system_statusGet CPU usage, RAM usage, GPU usage.
set_rgb_zoneSet the color of one keyboard zone.
apply_rgb_settingsApply mode, speed and brightness to all lights.

It also keeps the app state — things the app needs to remember while it's running, like the system-monitoring object and a little cache for GPU usage.

3. config.rs — the memory backend

When you set your fans and lights and quit the app, you probably want them back next time. This file saves your settings to a JSON file at ~/.config/nitrosense-linux/config.json.

It's also smart about safety: it writes to a temporary file first and then renames it. If the computer crashes mid-save, you don't get a half-broken config file. And if the config file is corrupt, it quietly resets to sensible defaults instead of crashing.

🛡️ The important safety ideas

Locking — "one at a time, please"

The hardware file /proc/acpi/call doesn't like two commands at the same time. To prevent chaos, the backend uses locks (called mutexes — short for "mutual exclusion"):

  • One lock keeps the app's own threads from sending hardware commands at the same moment.
  • Another lock (flock) makes sure other programs don't fight over the same hardware file at the same time.
Analogy: A mutex is like a public toilet with a lock. Only one person can use it at a time. Everyone else waits their turn, so nobody walks in mid-use.

Resetting fans on exit — a good citizen

If you set the fans to "max" and close the app, the fans would keep blasting at 100%. So the backend listens for the window being closed and politely resets the fans back to Auto. This is a safety net so you never walk away with your laptop roaring.

Caching — don't ask twice

Running nvidia-smi is slow (it's a whole separate program). So the backend caches the GPU usage for 4 seconds and only asks for a fresh value after that. This keeps the app fast and doesn't hammer the system.

Always-on application

The backend can also run in a special "apply" mode (--apply). This is used at boot/login to re-apply your saved fan and RGB settings without opening the window — just run it, apply, and exit.

🔄 The whole journey, start to finish

  1. You drag a slider to "80% fan speed" in the frontend.
  2. The frontend calls the set_fan_speed command.
  3. main.rs receives the call and hands it to wmi.rs.
  4. wmi.rs grabs the lock, builds the WMI command, writes it to /proc/acpi/call.
  5. The laptop's embedded controller reads the command and sets the fan speed.
  6. The command is confirmed, the lock is released, and the frontend shows "saved!"
So remember: the backend is a translator and bodyguard. It translates clicks into the laptop's secret language, keeps the hardware safe by locking and cleaning up, and never crashes the app — no matter what weird thing the hardware or the config file throws at it.
